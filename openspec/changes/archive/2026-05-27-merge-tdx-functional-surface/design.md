## Context

The external `D:\MyCode3\tdx` tree is not a clean upstream branch. It is a Windows-side working copy containing earlier source files, real-machine JSON evidence, historical docs, generated bytecode, and large raw probe dumps. The current repository already contains many later capabilities that are not present in `tdx`, including block sync, bridge HTTP control, provider transport replay, subscription background control, formula capability registry, function-tree validation, extended trade audit indexing, and broader test coverage.

The merge must therefore be capability-led rather than file-copy-led. `tdx` is treated as an evidence and historical-function source; `D:\MyCode3\TdxQuant` remains the implementation target and source of current truth.

## Goals / Non-Goals

**Goals:**
- Reconcile the three requested `tdx` documents and their functional claims against the current repository.
- Preserve newer current-repository behavior and avoid overwriting modules with older `tdx` copies.
- Update the single feature registry and operator-facing docs so PingAn and TongDaXin trading boundaries are accurate.
- Curate useful real-machine validation evidence into stable locations or documentation indexes.
- Add focused regression checks that protect the adopted boundaries.

**Non-Goals:**
- Do not bulk-copy `tdxquant/`, `tests/`, `runtime/`, or `docs/` from `D:\MyCode3\tdx`.
- Do not import generated files such as `__pycache__`, `.pytest_cache`, raw huge probe dumps, or unsanitized account-sensitive artifacts.
- Do not claim TongDaXin full live order submission is implemented.
- Do not change public CLI behavior unless a later implementation task discovers a concrete gap in current commands.
- Do not replace `FUNCTION_TREE.md` with a second roadmap or competing status document.

## Decisions

### 1. Use capability reconciliation instead of directory overwrite

Implementation will build a merge matrix by category:
- current repository already newer
- external-only useful evidence/documentation
- conflicting status claim requiring registry correction
- generated/noisy artifact to ignore
- sensitive artifact requiring redaction before any import

This avoids regressing the current implementation. A directory overwrite is rejected because `tdx` lacks several current modules and tests.

### 2. Treat `FUNCTION_TREE.md` as the adoption target

The final feature status must land in `FUNCTION_TREE.md`, with supporting docs linking back to it. `docs/TdxQuant_Project_Function_Map.md` can be updated as background/context, but must not become a second authoritative map.

### 3. Split PingAn and TongDaXin trading conclusions

The PingAn line can be adopted as validated mixed-chain desktop execution evidence when the registry and docs state the actual chain: UIA field entry, HID first confirmation trigger, Win32 `WM_COMMAND` confirmation, and HID final result close.

The TongDaXin line remains probe/diagnostic-only for trading execution. Existing TongDaXin bridge and HID probe commands can stay documented, but full live order submission cannot be marked available until the trading business layer accepts automated security-code input.

### 4. Curate evidence, do not archive every raw artifact

The implementation should import or reference a small set of stable evidence files and summaries. Large raw probe dumps can remain in `D:\MyCode3\tdx` as external historical material unless a task explicitly scrubs and indexes them. Imported evidence must be small enough to review and must avoid leaking account identifiers or contract numbers unless already intentionally recorded as test evidence.

### 5. Tests protect boundaries, not historical file equality

Verification should prefer current focused tests:
- `FUNCTION_TREE` registry validation
- desktop trade manager / gateway / CLI focused tests
- HID bridge tests
- TongDaXin bridge tests where they already exist

No test should assert that current files match the older `tdx` copy byte-for-byte.

## Risks / Trade-offs

- [Risk] Historical `tdx` evidence may contain account identifiers, contract numbers, or giant raw dumps. → Mitigation: import only curated/scrubbed artifacts and document external evidence paths when raw material should remain outside the repository.
- [Risk] README and function-map language can accidentally overstate TongDaXin trading support. → Mitigation: update status wording and add registry validation coverage for explicit unavailable boundaries where appropriate.
- [Risk] Current dirty worktree could mix unrelated changes into the merge. → Mitigation: keep this change scoped to OpenSpec artifacts first, then implementation tasks must review `git status` before edits and stage only relevant files.
- [Risk] PingAn evidence may be mistaken for pure Win32 automation. → Mitigation: require the mixed UIA/HID/Win32 chain to be named in docs and registry.
- [Risk] External docs and current docs may duplicate each other. → Mitigation: keep `FUNCTION_TREE.md` authoritative and demote older maps to background references.

## Migration Plan

1. Create the merge matrix from the requested documents and targeted directory comparisons.
2. Update registry/docs for status alignment before importing any new runtime evidence.
3. Curate a minimal PingAn/TongDaXin validation evidence index and optional sanitized artifacts.
4. Add or adjust focused tests only where status boundaries are machine-checkable.
5. Run focused test suites, then run the full pytest suite when practical.

Rollback strategy: because this is a documentation/evidence/status reconciliation first, rollback consists of reverting the changed docs/spec artifacts and any curated evidence files. No live trading behavior should change unless later tasks identify and implement a specific code gap.
