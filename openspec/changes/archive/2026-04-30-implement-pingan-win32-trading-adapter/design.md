## Context

仓库当前只有说明文档，没有可复用的交易适配代码。`docs/pa-sect-read.md` 已经给出 Win32 API 思路，但它默认能够直接通过控件文本识别输入框和按钮，这在真实券商客户端里并不总是稳定。当前还确认了一个运行环境事实：实际可执行文件在 Windows 为 `D:\ProgramData\PinganSec\TdxW.exe`，在当前 WSL 环境下对应 `/mnt/d/ProgramData/PinganSec/TdxW.exe`。

这个功能的本质不是“写一个买入脚本”，而是建立一个可验证的 Windows 自动化适配层，先解决路径、窗口发现、控件探测和失败反馈，再把交易动作封装成稳定接口。随着真实联调推进，这个目标已经拆成两条线路：

- 平安证券：保留探测/填单能力，但明确当前版本不承诺纯后台最终提交。
- 通达信：Win32/UIA 级验证已经覆盖合理路径，但当前环境下交易权限不可用，因此这条交易线暂时关闭，只保留历史验证资产和桥接探测能力。

## Goals / Non-Goals

**Goals:**
- 为平安证券客户端定义一个最小可交付的后台买入闭环。
- 将“可执行文件发现”和“Win32 控件驱动”拆成独立能力，避免路径逻辑与交易逻辑耦合。
- 要求先提供只读探测能力，再提供实际执行能力，降低误下单风险。
- 让后续实现可以在 Python 工程中直接落地，并为卖出、撤单、确认对话框处理保留扩展点。
- 沉淀 TongDaXin HID 路线的历史验证结论，但不再把它作为当前阶段的真实交易执行目标；后续交易执行主线改由 `PingAN + HID` 承担。

**Non-Goals:**
- 本次不要求实现卖出、撤单、委托回报查询和成交回读。
- 本次不要求完整支持多个券商客户端；当前阶段只继续推进 PingAn 真实交易执行线路，TongDaXin 交易线路暂时关闭。
- 本次不要求跨平台执行；交易执行明确限定在 Windows 环境，WSL 只承担路径发现和文档/开发辅助角色。
- 本次不要求绕过券商客户端的安全限制；若目标版本不接受 `WM_SETTEXT` 或 `BM_CLICK`，需要在后续变更中另行设计回退方案。
- 本次不要求实现通用 HID 固件生态，只要求给出一条可验证的基准实现，例如 Arduino Leonardo/兼容 HID 板卡。

## Decisions

### 1. 以 Python + `pywin32` 作为首个实现载体

选择 Python 是因为文档样例已经基于 `pywin32`，且窗口枚举、句柄操作和快速验证在 Python 中成本最低。当前仓库也没有现成的 Node/Go/Rust Windows 自动化基础设施，直接转到其他语言只会增加验证成本。

备选方案：
- Node 原生扩展：可行，但开发和调试成本更高。
- UIAutomation/图像识别：覆盖面更广，但和文档目标“后台消息、无鼠标操作”不一致。

### 2. 先实现“探测器 + 适配器”，再实现交易入口

控件识别是最大的不确定点，因此必须先实现两个层次：
- `RuntimeDiscovery`：解决客户端位置与启动入口。
- `WindowInspector` / `PingAnBrokerAdapter`：解决主窗口、控件树、控件匹配和页面状态。

只有当探测器稳定输出主窗口、代码框、价格框、数量框、买入按钮后，才允许进入 `buy()` 执行流程。

备选方案：
- 直接在 `buy()` 内部隐式枚举全部控件。这个方式短期快，但调试困难，失败时几乎没有定位信息。

### 3. 路径发现必须支持“显式配置优先，自动探测兜底”

当前用户给出的是 Windows 路径 `D:\ProgramData\PinganSec\TdxW.exe`，当前环境验证到的 WSL 映射是 `/mnt/d/ProgramData/PinganSec/TdxW.exe`。因此实现不能把路径硬编码成单一形式。

推荐解析顺序：
1. 用户显式传入的 `--exe-path`
2. 配置文件中的 Windows 路径
3. 配置文件中的 WSL 路径
4. 内置候选路径自动探测

这样可以兼容真实部署、WSL 开发以及未来安装目录变化。

### 4. 明确最小命令集

本次 change 只定义四个一阶命令能力：
- `inspect`: 输出主窗口和子控件树，供人工确认。
- `detect`: 输出识别到的关键控件句柄和匹配依据。
- `health-check`: 验证 exe 路径、主窗口、登录状态/买入页面前提是否满足。
- `buy`: 在前置校验通过后，写入证券代码、价格、数量，并发送买入动作。

这样既能先验证环境，也能把误操作风险前移。

在真实联调阶段，还需要额外提供三类低层能力，不直接承诺业务成功，只用于排障和归因：
- `win32-read`: 直接读取指定 `hwnd` 的类名、文本、父句柄、控制 ID 和矩形。
- `win32-set-text`: 直接对指定 `hwnd` 写入文本，并回读前后状态。
- `win32-click`: 直接对指定 `hwnd` 发送 `BM_CLICK`、`WM_COMMAND` 或 `ENTER`，验证客户端对非物理触发的接受程度。

### 5. 用结构化结果返回执行状态

每个命令都应返回结构化结果，而不是只打印文本。最少应包含：
- `ok`
- `message`
- `detected_path`
- `main_hwnd`
- `matched_controls`
- `warnings`
- `next_action`

这样后续可以很自然地挂 CLI、日志系统和策略引擎。

### 6. 通达信 HID 路线保留为历史验证资产，未来交易主线转向 PingAn + HID

真实联调已经证明，以下几类输入方式都不足以让通达信交易业务层认可证券代码输入：

- `WM_SETTEXT`
- `WM_CHAR`
- `WM_CHAR + Tab`
- `keybd_event + Ctrl+A + Delete + 逐字符输入 + Tab`
- `Stock` 注册消息切换主证券上下文

这些结论已经足够说明 TongDaXin 交易线的技术边界，但结合 `2026-04-30` 的实机结果，当前环境下交易权限不可用，因此不再继续推进这条真实交易闭环。后续真实交易执行主线改为 `PingAN + HID`，这里保留的内容仅作为历史验证资产和设计依据。

建议架构：

- WSL/策略侧：只负责生成交易请求和高层指令。
- Windows 主机侧代理：负责串口/USB 通信、窗口激活、焦点管理、Win32 探测和与 HID 设备协作。
- HID 设备：通过 USB 作为标准键盘枚举，发送真实按键序列到代码输入框。

最小闭环：

1. Windows 代理找到通达信买入页主窗口和代码框。
2. Windows 代理把窗口切前台并聚焦代码框。
3. 代理通知 HID 设备输入 `000001`，必要时附带 `Enter`/`Tab`。
4. Windows 代理继续沿现有 Win32 路径填充价格、数量并触发买入按钮。
5. 代理抓取弹窗正文与按钮，验证是否越过“请输入证券代码!”。

这样可以把现有验证积累复用起来：

- Win32/UIA 继续负责“探测、定位、读回、提交流程、弹窗抓取”
- HID 只负责“证券代码输入”这一条当前唯一核心阻塞点

## Risks / Trade-offs

- [控件文本可能为空或不稳定] → 匹配策略不能只依赖窗口文本，必须预留类名、父子层级、同级顺序和矩形区域等辅助信息。
- [不同版本客户端控件层级不同] → `inspect` 必须成为正式能力，而不是一次性调试脚本；同时需要保留 `hwnd` 级低层工具做最终归因。
- [WSL 能发现路径但不能直接执行 Windows GUI 自动化] → 规格中明确执行环境限定为 Windows 原生 Python；WSL 仅作为路径映射和开发环境参考。
- [误下单风险] → `buy` 必须依赖 `health-check` 和控件检测结果，且支持 dry-run 或“仅填充不点击”模式作为首轮验证。
- [确认弹窗/风控弹窗未处理] → 本次把弹窗处理列为后续扩展，不把“下单即成功”写进规格。
- [平安证券与通达信行为可能分叉] → 需要在规格和文档中分别记录“能填单”和“能提交”的验证结论，避免把某个客户端的失败外推到所有客户端。
- [HID 设备通信不稳定] → 需要约束设备固件协议，最小化指令集，只传递明确的“输入字符串/按键确认”命令并带 ACK。
- [HID 输入具有真实副作用] → Windows 代理必须先完成窗口激活和焦点校验，避免按键打到错误程序。
- [硬件依赖提高部署门槛] → 需要文档化硬件型号、刷写流程和 Windows 主机侧代理配置，降低复现实验成本。

## Migration Plan

1. 先在仓库中建立 Python 工程骨架和 Windows 适配模块。
2. 实现路径探测和控件树探测，只做只读验证。
3. 在真实客户端页面上固化平安证券买入页的匹配规则。
4. 增加 `buy` 最小闭环，并先通过 dry-run 验证。
5. 在确认真实控件行为后，再开启真实点击和后续弹窗处理。
6. 当 Win32/UIA 路径确认无法穿透交易代码输入校验后，引入 HID 键盘模拟方案，只替换代码输入环节。
7. 在真实 Windows 主机上验证 HID 输入是否能把交易弹窗从“请输入证券代码!”推进到真正的下单确认。

## Open Questions

- 平安证券当前安装版本的买入页控件文本是否可稳定读取，还是需要依赖邻接 `Static` 标签和控件顺序？这个问题对“填单”已基本确认，但对“最终提交”已不再作为默认前提。
- 通达信买入页当前绑定到的 `hwnd` 是否跨会话稳定，还是每次启动都需要重新探测？
- 通达信下单后是否一定会出现确认弹窗，还是部分环境可直接受理？
- 未来是否需要让策略进程运行在 WSL，而把 Windows 自动化封装为独立 sidecar 进程？
- Windows 主机侧代理是直接串口控制 Arduino Leonardo，还是通过本地小服务暴露 HTTP/IPC 接口更易集成？
- HID 输入完成后，代码框是否还需要额外的 `Enter`、`Tab` 或其他确认键序列，需在真实设备上验证。
