## Context

当前已有两层能力：

- `guarded_trade_buy` 负责执行并连续追加 ledger
- `ledger_summary` 负责读取、筛选和导出 ledger 记录

但日常使用里还有一个高频视角没有被覆盖：按“某个交易日”查看整体执行情况。这个视角关心的是：

- 当天总共执行了多少条
- 成功和失败各多少
- 哪些代码出现过
- 每个代码当天出现几次、累计数量多少、名义金额多少

## Goals / Non-Goals

**Goals:**

- 提供一个稳定的 `daily_trade_report` task。
- 按指定日期和时区过滤 ledger 记录。
- 输出总览摘要、按代码聚合结果和最近记录。
- 可选导出 JSON 全量报表和 CSV 聚合表。

**Non-Goals:**

- 不做跨月、跨周统计平台。
- 不引入数据库或 BI 层。
- 不修改已有交易执行逻辑和 ledger 结构。

## Decisions

### 1. 以 ledger 为唯一输入源

日报 task 不直接依赖交易执行流程，而只消费现有 ledger。这样：

- 交易路径和报表路径解耦
- 可重复生成历史报表
- 失败重跑报表不会影响交易行为

### 2. 用“交易日 + 时区”来定义报表边界

ledger 里的时间戳是 UTC 记录。日报 task 在聚合前先把时间戳转换到目标时区，再按本地日期过滤。默认使用 `Asia/Shanghai`，避免 UTC 跨日导致日报边界错误。

### 3. JSON 输出全量，CSV 输出按代码聚合

JSON 保留完整摘要、按代码统计和最近记录；CSV 则专注于最常用的按代码聚合视图，方便表格查看和后续手工处理。

### 4. 与 ledger summary 共享底层读取和过滤逻辑

把 ledger 读取、布尔字段规范化、通用过滤提成 helper，避免两个 task 分别维护类似逻辑。

## Risks / Trade-offs

- [时间戳格式不一致] → 对无法解析的记录跳过日期聚合，并把影响控制在匹配结果之外。
- [价格字段可能不是严格数值] → 聚合金额时按容错方式转换，无法转换则按 0 处理。
- [CSV 只输出按代码聚合，不含逐条明细] → 逐条明细继续由 `ledger_summary` 提供，避免日报输出重复职责。
