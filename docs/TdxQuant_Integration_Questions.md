# TdxQuant 跨项目集成待确认信息

本文用于收集上层项目对本项目的集成需求，帮助明确：

- 本项目应该以什么形式被复用
- 哪些能力必须优先稳定
- 哪些接口契约需要先固定
- 哪些能力不应下沉到本项目

建议由两个上层项目分别回答，再统一比对。

## 1. 复用方式

这是当前最关键的一组问题，因为它会直接决定本项目后续优先做 `CLI-first`、`SDK-first` 还是 `service-first`。

需要确认：

- Python 项目准备怎样调用本项目
- Rust 项目准备怎样调用本项目
- 两个项目是否允许采用不同调用方式
- 是否接受本项目主要作为 `Windows sidecar / provider` 被调用，而不是直接内嵌进 Linux/WSL 主进程
- 是否希望把本项目视为“补充 TongDaXin 特有能力的 provider”，而不是替代现有主数据/主任务系统

候选方式通常包括：

- 直接调用 Python manager / task
- 调用 CLI 并读取 JSON 输出
- 调用本地常驻服务
- 调用 Windows 侧 provider，再通过 HTTP / JSONL / 文件协议消费结果
- 通过状态文件 / 结果文件 / 事件文件集成
- 混合模式

建议上层项目给出一个真实示例：

- 谁调用
- 调哪个能力
- 希望拿到什么结果

## 2. 运行环境与部署约束

需要确认：

- 上层项目运行在 Windows、WSL、Linux 还是混合环境
- 上层项目是否接受“Linux/WSL 主进程 + Windows provider”这种跨主机或跨运行时模型
- 是否允许依赖本地安装的通达信客户端
- 是否接受 TongDaXin 原生能力只能在 `native Windows Python` 侧真正执行
- 是否允许本项目以常驻进程方式运行
- 是否允许桌面前台自动化
- 是否需要支持远程主机调用本地通达信能力

这些问题会影响：

- 路径方案
- 进程模型
- provider 部署模型
- 日志与状态文件位置
- 是否要优先做本地 daemon

## 3. 核心能力优先级

需要确认两个上层项目各自最关心哪些能力。

建议按重要性排序：

- 行情查询
- 公式计算
- 自定义板块管理
- 财务数据
- 交易统计数据
- 实时订阅
- 客户端预警
- 报表任务
- 桌面自动化交易

这会直接影响本项目后续是优先建设：

- 查询 API
- 长驻订阅任务
- 报表入口
- 交易执行入口

还需要额外确认接入顺序是否接受以下分层：

- 第一层：只读能力优先，例如 `formula / market / meta / financial / transaction`
- 第二层：实时订阅与事件流
- 第三层：板块同步
- 第四层：桌面自动化交易，且仅作为 `experimental / manual-confirmed / broker-specific`

## 4. 结果契约与输出协议

需要确认上层项目期望怎样消费结果。

重点包括：

- 返回结构优先用 `JSON`、`JSONL`、`CSV` 还是多种并存
- 是否需要固定 schema
- 是否需要字段版本号
- 是否需要统一错误码
- 是否需要统一耗时信息
- 是否需要统一 capability version
- 是否需要统一 artifact path 字段命名
- 是否需要统一 metadata，例如：
  - `source`
  - `session_id`
  - `profile`
  - `runtime`
  - `started_at`
  - `elapsed_ms`

这决定本项目是否需要尽快把“输出协议”视为正式接口，而不是仅供人工阅读的结果。

如果上层项目要消费实时订阅，还需要确认事件流的标准载体：

- `JSONL`
- `HTTP stream / SSE`
- `Redis`
- 本地状态文件 + 轮询
- 其他消息通道

以及是否需要：

- event schema version
- reconnect metadata
- subscription session state
- canonical event envelope

## 5. 稳定性与版本治理要求

需要确认：

- 上层项目是否需要长期稳定调用契约
- 是否接受“接口名称 / 输出字段会持续调整”
- 是否需要语义化版本
- 是否需要 capability 级版本标记
- 是否需要为 task / preset / catalog 入口提供兼容承诺

如果上层项目是长期依赖方，这部分就不能再靠“默认兼容”来处理，必须明确版本治理策略。

## 6. 能力探测与健康检查要求

需要确认上层项目是否希望在调用前就知道“当前哪些能力可用”，而不是失败后再猜。

典型探测项包括：

- 当前平台是否支持
- TongDaXin 是否启动
- `TPythClient.dll` 是否可用
- 实时订阅 runtime 是否可用
- 串口 / HID 是否可用
- 窗口探测是否可用
- 当前哪些 capability 可调用

如果这是刚需，本项目应优先建设统一的 `capability doctor / runtime doctor / health probe`。

## 7. 性能与吞吐要求

需要确认：

- 哪些调用是低频人工使用
- 哪些调用是高频程序调用
- 是否存在批量股票、批量板块、批量公式场景
- 对实时订阅延迟是否有明确要求
- 是否需要记录全流程耗时
- 是否需要提供性能剖析信息

这会影响：

- 是否优先做缓存
- 是否要做批量任务接口
- 是否需要单独的长驻 session / daemon

## 8. 状态、日志与审计要求

需要确认：

- 是否需要每次任务保留状态文件
- 是否需要统一事件日志
- 是否需要交易、订阅、报表分别建台账
- 是否需要机器可读日志
- 是否需要支持失败重试和断点恢复

如果上层项目更重视审计和可追踪性，本项目就需要尽快统一：

- 日志目录
- 状态目录
- 结果目录
- 文件命名规则

## 9. 责任边界

需要确认哪些逻辑应当放在本项目，哪些逻辑应保留在上层项目。

建议明确划分：

- 本项目负责：
  - 通达信能力适配
  - 标准化查询 / 公式 / 板块 / 订阅 / 客户端联动
  - 桌面自动化交易能力
  - 稳定 task / report / catalog 入口
- 上层项目负责：
  - 策略逻辑
  - 风控逻辑
  - 投资组合管理
  - 调度编排
  - 业务级决策

如果这条边界不清楚，本项目后续很容易继续膨胀。

还需要确认：

- 上层项目是否把本项目当成“TongDaXin 特定能力 provider”
- 是否明确不让本项目替代上层现有主数据服务、主 API 契约和主任务治理
- 是否接受 query path 与 trade path 在接入策略上完全分离

## 10. 跨语言复用的特殊问题

因为你有一个 Python 项目和一个 Rust 项目，建议额外确认：

- Rust 项目是否愿意通过 CLI + JSON 协议调用
- Rust 项目是否必须要本地服务接口
- Python 项目是否更希望直接 import 本项目
- 两个项目是否都需要相同的 task / preset / catalog 名称
- 是否需要为跨语言调用提供更薄的“公共协议层”

如果两边调用方式明显不同，本项目后续可能要同时维持：

- Python 原生调用面
- 语言无关调用面

## 11. 写入类与交易类能力的风险偏好

需要确认上层项目对写入型能力的接受程度，尤其是：

- `send_warn`
- `send_user_block`
- 自定义板块生命周期修改
- 桌面自动化交易

建议明确：

- 哪些能力可以直接进入主线
- 哪些能力只能先走 `experimental`
- 哪些能力必须 `manual-confirmed`
- 哪些能力需要 broker-specific 隔离

如果未来涉及交易，还需要确认是否要求：

- 幂等 submission key
- pre-trade risk gate
- 二次确认策略
- durable audit log
- broker / runtime health check

## 12. 建议上层项目优先给出的信息

如果不想一次回答太多，建议至少先确认以下 6 项：

1. Python 项目准备怎样调用本项目。
2. Rust 项目准备怎样调用本项目。
3. 两个项目各自最常用的 3 个能力是什么。
4. 期望返回结果是 `JSON`、`JSONL`、`CSV` 还是混合。
5. 是否允许本地常驻进程或 daemon。
6. 哪些逻辑必须留在上层项目，不能下沉到本项目。

如果希望更快形成接入结论，建议再补 4 项：

7. 是否接受 `Windows sidecar / provider` 作为默认接入模型。
8. 是否接受“只读能力 -> 订阅 -> 板块同步 -> 交易实验线”这个接入顺序。
9. 实时事件流优先希望走什么通道。
10. 是否需要 `capability doctor / runtime doctor`。

## 13. 建议的收集方式

建议让两个上层项目分别按下面模板回答：

```md
## 项目名称

### 调用方式

### 是否接受 Windows provider 模式

### 核心场景

### 运行环境

### 输出协议

### 实时事件通道

### 能力探测 / 健康检查需求

### 稳定性要求

### 接入顺序偏好

### 写入类 / 交易类风险偏好

### 不希望下沉到 TdxQuant 的逻辑
```

这样可以最快把“共同需求”和“分歧需求”分出来。
