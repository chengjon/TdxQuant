# 通达信 HID 硬件键盘模拟方案

## 1. 背景

前一阶段已经验证：

- 平安证券当前版本可探测、可填单、可读状态，但未证明纯非物理最终提交闭环。
- 通达信当前版本可完成切股、填价、填量、非物理触发 `买入下单`，但交易业务层始终拒绝纯 Win32/UIA 路线写入的证券代码。
- 典型失败弹窗正文稳定为：`请输入证券代码!`

因此后续主路线不再继续深挖 Win32/UIA 级“后台代码输入”，而是改为：

- 保留 Win32/UIA 作为“探测、定位、读回、提交、弹窗抓取”层
- 把“证券代码输入”替换为 HID 硬件键盘模拟产生的真实按键事件


## 2. 目标

最小目标不是“一步到位量产”，而是先验证下面这条闭环：

1. Windows 代理定位通达信买入页代码框
2. Windows 代理确认目标窗口在前台且焦点正确
3. HID 设备输入证券代码，例如 `000001`
4. 必要时补发 `Enter` 或 `Tab`
5. Windows 代理继续用现有 Win32 链路填充价格、数量
6. Windows 代理非物理触发 `买入下单`
7. 抓取弹窗，确认是否越过 `请输入证券代码!`

如果这条链路成立，就说明当前唯一核心阻塞点确实是“代码输入必须来自系统认可的真实键盘事件”。


## 3. 架构

```text
┌────────────────────┐
│ WSL / 策略侧        │
│ 生成交易请求        │
│ code/price/qty     │
└─────────┬──────────┘
          │ 文件/HTTP/CLI
          ▼
┌────────────────────┐
│ Windows 主机代理    │
│ - 激活通达信窗口     │
│ - 探测代码框/价格框  │
│ - 焦点校验          │
│ - 串口发命令给 HID   │
│ - Win32 填价填量     │
│ - Win32 触发提交     │
│ - 抓取提示弹窗       │
└─────────┬──────────┘
          │ USB CDC / Serial
          ▼
┌────────────────────┐
│ HID 键盘设备        │
│ - 枚举为标准键盘     │
│ - 接收简单串口命令   │
│ - 输出真实按键序列   │
└────────────────────┘
```

职责边界：

- WSL / 策略侧：只负责下发高层请求，不直接碰 GUI。
- Windows 主机代理：负责所有“会话态”判断，包括前台窗口、焦点、弹窗、句柄、风险保护。
- HID 设备：只负责稳定输出真实按键，不承担业务判断。


## 4. 硬件基线

建议首选：

- Arduino Leonardo
- Arduino Micro
- 任何原生支持 USB HID Keyboard 的 ATmega32u4 板卡

不建议首轮使用：

- 仅串口、不能枚举为键盘的普通 USB 转串口板
- 依赖厂商专有驱动的注入设备
- 需要复杂固件生态的多功能开发板

原因：

- Leonardo/Micro 成本低
- Windows 识别为标准键盘，兼容性最好
- Arduino `Keyboard` 库成熟，原型验证最快


## 5. 最小通信协议

首轮协议只做一件事：让 HID 设备按要求输入字符串和确认键。

建议使用串口文本协议：

```text
PING
TYPE 000001
TYPE 000001 TAB
TYPE 000001 ENTER
KEY TAB
KEY ENTER
```

设备返回：

```text
OK PONG
OK TYPE 000001
OK KEY TAB
ERR UNKNOWN_CMD
```

约束：

- 一条命令只做一件事
- 命令必须同步 ACK
- 不支持脚本、宏、循环等高风险能力
- 不允许代理一次下发任意原始按键流

这样做的目的不是追求通用，而是缩小副作用面。


## 6. Windows 主机代理设计

### 6.1 输入前置校验

在调用 HID 之前，代理必须同时满足：

- 找到目标主窗口，标题匹配通达信交易终端
- 找到买入页代码框
- 当前前台窗口句柄就是目标通达信窗口
- 当前焦点在代码框，或代理刚刚成功把焦点切到代码框

任一条件不满足，都必须拒绝发送 HID 输入。

### 6.2 输入步骤

建议顺序：

1. 激活通达信主窗口
2. 切到买入页
3. 聚焦代码框
4. 发送清空序列
5. 调用 HID 输入证券代码
6. 视验证结果补发 `Tab` 或 `Enter`
7. Win32 读回价格/数量框并填充
8. 用现有最优提交策略 `post_wm_command_parent` 触发 `买入下单`
9. 抓取弹窗正文和按钮

### 6.3 清空策略

由于 HID 将被系统视为真实键盘，清空也应走真实按键：

- `Ctrl+A`
- `Delete`

这两步应由 HID 设备执行，而不是由 Win32 `WM_SETTEXT` 执行，以免再次落入“控件有文本但业务层不认”的老问题。

### 6.4 结果模型

建议代理输出结构化 JSON：

```json
{
  "ok": true,
  "phase": "submit",
  "window_title": "买入股票",
  "code_input_mode": "hid",
  "hid_command": "TYPE 000001 TAB",
  "price": "10.00",
  "quantity": "100",
  "submit_method": "post_wm_command_parent",
  "popup_text": "请输入证券代码!",
  "warnings": []
}
```

这样可以直接用于回归比较。


## 7. HID 固件设计

固件只保留三个能力：

- `PING`
- `TYPE <digits> [TAB|ENTER]`
- `KEY <TAB|ENTER|ESC>`

实现原则：

- 输入间隔固定，例如 30ms 到 80ms
- 每个字符都走 `Keyboard.press` / `Keyboard.release`
- 命令完成后才返回 `OK`
- 默认不实现组合宏，避免误触

首轮不需要：

- OLED 显示
- 本地按键
- 持久配置
- 多窗口感知

这些都应留在 Windows 代理层处理。


## 8. 安全边界

HID 路线比 Win32/UIA 更接近真实操作，所以必须明确安全边界。

必须有：

- 前台窗口校验
- 焦点控件校验
- 低价不成交测试模式
- 每次只执行单条命令
- 代理侧超时和失败即停
- 全量日志

建议有：

- `--dry-run`：只做窗口/焦点校验，不发 HID
- `--test-code-input`：只输入代码，不填价填量不提交
- `--confirm-popup-only`：只抓弹窗，不自动点确认

当前阶段禁止：

- 后台隐藏输入
- 无窗口校验直接发 HID
- 允许策略端直接下发任意按键脚本


## 9. 测试计划

### 9.1 阶段一：纯输入验证

目标：

- 证明 HID 输入后，通达信代码框被业务层真正接受

步骤：

1. 打开通达信买入页
2. 聚焦代码框
3. 发送 `TYPE 000001`
4. 分别测试无确认键、`TAB`、`ENTER`
5. 观察是否自动带出证券名称或上下文变化

成功信号：

- 不再出现 `请输入证券代码!`
- 或买入页出现证券名称/价格联动

### 9.2 阶段二：半闭环验证

目标：

- 代码输入走 HID，价格数量走 Win32

步骤：

1. HID 输入 `000001`
2. Win32 填充价格 `10.00`
3. Win32 填充数量 `100`
4. Win32 触发 `买入下单`
5. 抓取弹窗

成功信号：

- 弹窗进入真正的下单确认，而不是 `请输入证券代码!`

### 9.3 阶段三：低风险完整验证

目标：

- 用低价不成交方式验证整条链路可重复

步骤：

1. 选择当前明显无法成交的低价
2. 重复多轮相同命令
3. 对比日志、弹窗、委托状态

成功信号：

- 输入与提交流程稳定
- 不依赖人工物理点击
- 不因为窗口轻微抖动而失效


## 10. 实施顺序

建议按下面顺序开发：

1. 固化 Windows 主机代理接口
2. 写最小 Arduino HID 固件
3. 做 `PING` / `TYPE 000001` 单点验证
4. 做代码框焦点与清空验证
5. 接入现有 Win32 填价填量逻辑
6. 接入现有 `post_wm_command_parent` 提交逻辑
7. 加入弹窗抓取和日志
8. 最后再考虑与 WSL/策略侧对接


## 11. 最终结论

在当前验证基础上，HID 硬件键盘模拟是下一条最有效、最有希望打通的路线。

原因很明确：

- 当前唯一未解决核心阻塞点，是通达信业务层不认可 Win32/UIA 生成的证券代码输入。
- HID 能把“证券代码输入”提升为系统认可的真实键盘事件。
- 现有 Win32 能力并未浪费，仍可继续承担探测、提交和弹窗抓取。

所以后续正确路线不是“全部重做”，而是：

- 用 HID 替换代码输入
- 用现有 Win32 资产保留其余链路

这也是当前阶段投入产出比最高的方案。
